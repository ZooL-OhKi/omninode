# Bounded screenshot native transport

Screenshots are compacted in memory before native base64 serialization. Small payloads within 1280x800 remain unchanged. Larger images are downscaled to fit 1280x800 and JPEG-encoded under 600 KiB, leaving headroom inside the 1 MiB native JSON message limit. Source bytes are capped at 16 MiB and decoded source dimensions at 33,554,432 pixels. Original source dimensions and preview dimensions remain separate. Pixel coordinates describe the source image; native Windows DPI/multi-monitor calibration remains unverified. No image is written to disk by this conversion. The popup accepts only PNG/JPEG previews.

Executed in assistant environment: 7 image/serialization unit tests passed using generated image data. A real isolated Linux Chromium extension connected to a temporary Python fixture host via Chrome Native Messaging, completed the handshake and received a correlated JPEG preview (1600 source width, 1280 preview width, sequence 0) below the message limit. The committed test_native_browser.py was also run as a separate unittest process and passed. The host fixture generates an image: it never captures the actual desktop or auto-approves the production consent UI. The fixture uses a minimal test extension, not the production popup. CI now includes this explicit integration test; default discovery skips it unless opted in.

No user's screen was captured. No Windows install, registry or consent flow, physical mouse/keyboard input, real AI account, automatic chat attachment or multi-AI collaboration was tested. Those remain incomplete. Earlier notes about unconditional failure for large native screenshots are superseded within these resource caps; arbitrary-size or malformed images still fail closed. No deployment, local-copy update or merge is performed by this patch.
